# Friction log

Entries written as they happened during the build. Each entry: what I tried, what happened, what the docs say / whether a better approach exists, and a verdict — `my mistake` / `docs gap` / `real API friction`.

## Phase 1: docs verification + scaffold

- **What I tried**: looked up `agent.generate()` structured output via web search first; a GitHub issue surfaced `experimental_output` as a known-flaky option ("invalid JSON response" errors even with a Zod schema supplied).
- **What happened**: the current docs page (`docs/agents/structured-output`) uses a different, newer option name: `structuredOutput: { schema }`, with the result on `response.object`.
- **What the docs say**: `structuredOutput` is the current API; `experimental_output` appears to be an older/parallel path with known issues per a linked GitHub discussion.
- **Verdict**: docs gap (in my own search ordering, not Mastra's) — worth flagging in the observation anyway, since a model answering from memory or from a stale blog post would very plausibly reach for `experimental_output` and hit exactly the flakiness that issue describes.

## Phase 2: typing the parallel step's output into the synthesizer's input schema

- **What I tried**: a `specialistStep(id: string, agent)` helper that calls `createStep({ id, ... })` for each of the five specialists, to avoid repeating the same step boilerplate five times.
- **What happened**: TypeScript failed to unify `.parallel([...]).then(synthesizeStep)` — the synthesizer step's `inputSchema` names five literal keys (`engineer`, `product`, ...), but because the helper's `id` parameter was typed as plain `string`, TypeScript widened every step's id to `string`, so the inferred parallel output type was `{ [x: string]: SpecialistView }` instead of a keyed object with the five literal properties. The two didn't unify.
- **What the docs say**: the docs' own parallel example never factors step creation into a helper — each `createStep({ id: 'literal-id', ... })` is written out by hand, which sidesteps this entirely because each `id` is already a string-literal type at the call site.
- **Verdict**: real API friction (a docs/type-inference gap, not a runtime one) — the parallel-step API's "combined output keyed by id" design is only as type-safe as each id being inferred as a literal, which silently breaks the moment you extract a helper function, and the error message (a wall of structurally-expanded types) gives no hint that the fix is "make id generic." Fixed by making the helper generic over `Id extends string` so each call site's literal is preserved.

## Phase 4: parallel branches were invisible as a single trace, by default

- **What I tried**: ran the workflow end-to-end with `MastraStorageExporter` configured, then queried `/api/observability/traces` while `mastra dev` was running against the same SQLite file.
- **What happened**: instead of one trace for the workflow run with five parallel child spans (what phase 4's "done" criteria asks for), I got **seven completely disconnected root traces** — one for the workflow, one for each of the five specialist `agent.generate()` calls, and one for the synthesizer. Each had its own random `traceId` and `parentSpanId: null`. There was no way to look at one trace and see "these five ran in parallel under this workflow" — you'd have to correlate them by timestamp instead.
- **What the docs say**: no single doc page states this plainly, but a Mastra changelog entry (fixing `createStep(myAgent)` composition) implied the fix: `tracingContext` has to be explicitly threaded from the step's `execute({ inputData, tracingContext })` params into `agent.generate(prompt, { tracingContext, ... })`. It is not automatic when you write your own `execute` function and call `agent.generate()` yourself inside it — only the shorthand `createStep(someAgent)` form (which I couldn't use here, since each step needs custom prompt-building logic) gets this wired up for free.
- **Verified fix**: added `tracingContext` to the destructured execute params in every step and passed it straight through to the corresponding `agent.generate()` call (2-line change per step). Re-ran and confirmed via the full trace endpoint: one `workflow run: 'deliberation'` root, with a `parallel: '5 branches'` child, five `workflow step` → `agent run` → `llm` chains under it (all five starting within 2ms of each other, confirming true concurrency), then `workflow step: 'synthesize'` after.
- **Verdict**: real API friction. This is exactly the kind of thing likely to bite someone building a multi-agent workflow: the moment you need custom logic around an agent call inside a step (which is almost always, since the shorthand `createStep(agent)` only covers the trivial passthrough case), you silently lose trace nesting unless you know to forward `tracingContext` yourself — and nothing surfaces an error or warning when you don't; the traces just quietly come out flat.

## Phase 5: wiring the browser UI to a live run via `@mastra/client-js`

- **What I tried**: reused the server-side pattern for structured output — pass the same Zod schema (`specialistViewSchema`) straight into `agent.generate(prompt, { structuredOutput: { schema } })` from the browser client, the way `src/mastra/workflows/deliberation.ts`'s own steps already do server-side.
- **What happened**: the client SDK's `structuredOutput.schema` type is `JSONSchema7`, not a Zod object — `SerializableStructuredOutputOptions` (the type actually used by `@mastra/client-js`'s `generate()`) explicitly omits Zod schema support, because the schema has to be serialized into an HTTP request body, not passed in-process.
- **What the docs say**: the client-js docs' `structuredOutput` example is a bare `{}` with no schema shown, so nothing there flags the Zod-vs-JSON-Schema split; it only became clear from reading the installed package's own `.d.ts` files (`SerializableStructuredOutputOptions` vs. the server-side `StructuredOutputOptions`).
- **Verdict**: docs gap — someone porting a server-side `structuredOutput` call to the client (a very natural thing to do, since the call otherwise looks identical) will reach for the same Zod schema and get a type error at best, a confusing runtime failure at worst. Fixed by mirroring the schema as a Zod object locally (kept in sync by convention with the backend's `src/mastra/schemas.ts`, not imported across the boundary) and converting with `z.toJSONSchema(schema, { target: "draft-7" })` at the call site.

- **What I tried**: called `agent.generate(prompt, { structuredOutput: { schema: jsonSchema } })` on the client without an explicit type parameter, relying on inference the way the server-side call does.
- **What happened**: `error TS2590: Expression produces a union type that is too complex to represent.` — the client's `generate<OUTPUT extends {}>` overload tries to infer `OUTPUT` from the JSON Schema object's own (large, `zod`-generated) type, and the inference blows up.
- **Verdict**: real API friction — the fix is mechanical once you know it (`agent.generate<SpecialistView>(prompt, { structuredOutput: { schema } })`, explicitly parameterizing the generic instead of letting it infer from the schema shape), but the error message gives no hint that "add an explicit type argument" is the fix.

- **What I tried**: planned the streaming integration around `docs/workflows/overview` and `reference/streaming/workflows/stream`, which describe `run.stream()` returning a `WorkflowRunOutput` with `.fullStream`, `.result`, and `.status`.
- **What happened**: `@mastra/client-js`'s `Run.stream()` (the browser-facing method actually available here) has a different, simpler signature — `Promise<ReadableStream<StreamVNextChunkType>>`. There's no `.fullStream`/`.result`/`.status` wrapper on the client; you get the raw stream and iterate it directly with `for await`.
- **What the docs say**: those two pages describe the `@mastra/core` (server-side) API, not `@mastra/client-js`'s wrapper around the equivalent HTTP endpoint, but nothing on the page signals that distinction — it reads as one unified "how workflow streaming works" story.
- **Verdict**: docs gap. Caught by reading `node_modules/@mastra/client-js/dist/resources/run.d.ts` directly rather than the docs, before writing any code against the wrong shape.

- **What I tried** (my own bug, not Mastra's): triggered the recovery-path's direct synthesizer call the moment all five specialists reached `complete`, checked on every incoming stream event.
- **What happened**: on the ordinary happy path, all five specialists can legitimately finish (via the stream) slightly before the workflow's own `synthesize` step actually starts — "all five complete" doesn't yet mean "the workflow has concluded without reaching synthesize." The premature check fired the client-side recovery synthesis call at the same time the real workflow was about to run its own synthesize step, racing two synthesis calls against each other.
- **Verdict**: my mistake, caught by the engine's unit tests before it ever touched a real server — worth remembering as a general trap for this shape of problem: "every branch of a fan-out finished" is not the same signal as "the process orchestrating them won't do anything further on its own." The recovery check only belongs after the stream itself has ended (or after a manual retry, which by construction only happens post-conclusion), never as a live per-event check.

## Smaller friction, noted but not the headline

- `LibSQLStore` requires an `id` field in its config (undocumented in the example I found) alongside `url` — TS caught this at compile time, so low-cost, but the docs example I fetched for "minimal local tracing setup" omitted it. Verdict: docs gap.
- Sharing trace storage between `mastra dev` and a separate CLI script (`tsx src/run.ts`) only works if the `LibSQLStore` `url` is an absolute file path — a relative path resolves against each process's own cwd, so the two processes silently write to two different database files. The docs do call this out explicitly (a rare case of the docs pre-empting the exact mistake I was about to make). Verdict: none — docs got there first.
- The documented convenience CLI, `npx mastra api trace list '{"page":0,"perPage":20}'`, returned a `401 Unauthorized` against a local `mastra dev` server with no auth configured anywhere in the project. The raw REST endpoint it wraps (`GET /api/observability/traces`) works fine unauthenticated. Verdict: real API friction, but minor — worked around by hitting the REST endpoint directly.
